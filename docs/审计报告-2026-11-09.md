### P0-01 · `GET /api/settings` 无鉴权明文回吐全部密钥，且 setting 表与 `audit_log` 各存一份明文

- **位置**：`app/server.mjs:126-136`（读：126-130；写：132-136）；明文写入口 `app/db.mjs:417`；审计落库 `app/db.mjs:419`
- **证据**（4 路独立实测，原始输出互相印证）：
  - `GET http://127.0.0.1:8795/api/settings` → 200、2418 B、38 个键，其中 4 个是真密钥明文：`image_api_key`（`sk-ncH1…`，51 字符）、`image_api_backup_key`（`sk-MLB1…`，51 字符）、`image_api_fallback_key`（`sk-uCs14…`，51 字符）、`postiz_api_key`（`e77f…348f`，64 字符）。
  - 源码 `server.mjs:126-130`：`for (const r of all('select k, v from setting order by k')) out[r.k] = r.v; return { settings: out };` —— 无白名单、无脱敏。
  - 同进程内口径自相矛盾：`GET /api/channels/postiz` 只回 `"key_hint":"…40fc"`；`GET /api/models`（`server.mjs:242`）只 select `key_hint`；`/api/ledger`（`server.mjs:1860`）文案还写着「Key 只显示后四位」。
  - 库副本（`.tmp/audit/workbench.db`，只读）confirm：setting 表里 4 个值均为明文，非 `v1.iv.tag.ct` 密文格式；而 credential 表存的是密文 `v1.S4kA3lpvZ8sEWXOo.uB/qQun6brl4F0`，`model_endpoint` 用 `api_key_cipher` —— 加密能力（`crypto.mjs:52`）存在，只用在 `server.mjs:231/250/261`，setting 完全绕过。
  - 第二份明文在审计表：`select id,action,detail from audit_log where action like 'settings%'` 返回 4 条含明文，如 id=177 `{"image_api_base":"https://tokenstation.top/v1",…,"image_api_key":"sk-ncH1…"}`、id=194 `{"postiz_api_key":"e77fa9…"}`；`select count(*) from audit_log where detail like '%sk-%'` = 4。即同一个 Postiz key 一份在 credential（密文、只回 hint），另一份在 audit_log（明文、永久留存），且 audit_log 目前没有任何路由读取，纯属多余暴露。
  - 暴露面不止本机：`server.mjs:18` `HOST = process.env.SWB_HOST || '127.0.0.1'`，而 `service/run.cmd:13` 注释明确写「要让同局域网别的设备访问，把下面一行改成 0.0.0.0」——照做后这些密钥对整个网段明文可读。`/api/overview` 的 `cryptoWeak:false` 只读环境变量 `SWB_CRYPTO_WEAK`，与四个 key 实际明文存储无关，是假绿灯。
- **修**：
  1. 读路径按键名脱敏：`const SECRET = /(_key|_token|secret|password)$/i;` 命中时返回 `{ set: !!v, hint: v ? String(v).slice(-4) : '' }` 而非 `v`；需要真值时另开 `POST /api/settings/reveal` 并校验来源。
  2. 写路径接上加密：`132-136` 对 SECRET 命中字段 `setSetting(k, encrypt(String(v)))`，`imageApiCfg()/imageApiBackupCfg()/imageApiFallbackCfg()`（`server.mjs:1172-1196`）读取处 `decrypt()`，与 `server.mjs:250` 的模型密钥同一写法。
  3. 审计只记键名：`audit('settings.update','',{ keys: Object.keys(b||{}) })`，并对库里已存在的 4 条明文 detail 与 4 条明文 setting 做一次性覆盖。
  4. 这 4 个已泄露的 key 在服务商侧轮换（tokenstation.top / apimart.ai / Postiz）。

### P0-02 · 发布结果无条件写成功：`publish_result.ok` 是 SQL 里的字面量 `1`，从不读适配器返回的 `r.ok`

### P1-03 · 分发器在 try 之外解析 Host 头，畸形 Host 触发未捕获 TypeError 让 node 进程直接退出

- **位置**：`app/server.mjs:1922-1943`（崩点 `1923`）

### P1-05 · 请求没有任何来源校验，且 `body()` 不看 Content-Type 就 `JSON.parse`，任意网页可用 `text/plain` 简单请求盲写服务状态

- **位置**：`app/server.mjs:1932`、`app/server.mjs:37-51`
- **证据**：`const b = ['POST','PUT','PATCH'].includes(req.method) ? await body(req) : {};`，`body()` 只判长度/空串/JSON 合法性，不检查 content-type。实测 `POST /api/models/test`，带 `Content-Type: text/plain` + `Origin: http://attacker.example` + body `{"base_url":"http://127.0.0.1:8795"}` → **200** `{"ok":false,"error":"HTTP 404 not found"}`（响应头 `access-control-allow-origin` 为空，跨域读被拦，但请求已执行，属无需预检的简单请求）。落到写接口即盲 CSRF：`585-594` 的 `POST /api/contents/(\d+)/review` 用同一个 b 直接 `update content set status='approved'`，攻击页可对 id 1..60 盲发 `{"decision":"approve"}` 全量放行，随后 3 秒一次的 tick 按排期发布。

### P1-07 · 排期认领与 job 插入不在同一事务，中断即丢单，排期永久卡 `queued`

- **位置**：`app/queue.mjs:62-65`
- **证据**：`L62` 先 `update schedule set state='queued' where id=? and state='pending'` 认领，`L64-65` 才 `insert into job`，两条之间无 BEGIN/COMMIT。库副本上用触发器让 job 插入 abort 模拟进程死在这条缝里，实测：`schedule 905: {"id":905,"state":"queued","run_at":"2026-11-09 09:39:39","err":""}`、`job for 905: []`；再跑 3 轮 tick 后仍是 `state":"queued"`、`publish_result for 905: []`、`orphan 统计: [{"id":905}]`、`enqueueDueSchedules 候选集命中: [{"c":0}]`。因为 `L46` 只捞 `pending`，这条排期永远不再执行，界面显示「已排队」。仓库根还留着未生效的补丁脚本 `fix-queue-race.mjs`（L11-12 与 `queue.mjs:62` 同一条 claim，多了一句无条件置 queued），说明此处被改过一次仍非原子。
- **修**：`62-65` 包 `BEGIN IMMEDIATE` … `COMMIT`，catch 里 `ROLLBACK`；tick 开头补同事务 reaper：`update schedule set state='pending', last_error='recovered' where state='queued' and id not in (select json_extract(payload,'$.schedule_id') from job where state in ('queued','running','retry'))`。

### P2-09 · 迁移无版本号、不在事务内，只有 3 张表有 ALTER 守卫，队列依赖的列无任何补齐路径

### P2-10 · `decrypt` 保护不一致：一处把密钥故障裸抛成 400，另一处吞错伪装成「缺凭据」
